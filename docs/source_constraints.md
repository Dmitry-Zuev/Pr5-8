# Источники решений и ограничения

## Подтверждено отчётом практических №1–4

- Предметная область: спортзал (фитнес-клуб).
- Шесть агрегатов: пользователь, абонемент, оплата, тренировка, отзыв, экскурсия.
- Четыре ограниченных контекста: управление пользователем; управление тренировками; управление абонементами и оплатой; экскурсия.
- PostgreSQL для контекстов; PostgreSQL + Redis для контекста тренировок.
- Синхронный REST для проверок; в первоначальном отчёте №1–4 асинхронным брокером указан Kafka.
- Правила: подтверждение оплаты → активация абонемента; расторжение → возврат денег; отзыв после завершения тренировки; планирование экскурсии менеджером после подтверждения.

## Уточнено пользователем для практик №5–8

- Последняя цифра студенческого билета: **3**. По методичке это вариант №3: `auto_delete` очередь, `fanout` обменник, случайная задержка `[1, 5]` секунд.
- **RabbitMQ вместо Kafka во всей асинхронной части проекта**. Это новое решение относительно №1–4. Синхронные REST проверки сохранены для выполнения №6.

## Предложено в прототипе, не выдается за ранее согласованное

- 6 FastAPI-приложений по шести агрегатам в четырех контекстах (разбиение учитывает требование не менее 2 сервисов на каждого из 3 авторов работы №1–4).
- Называния HTTP-эндпоинтов, таблиц, полей, RabbitMQ очередей/exchange и JSON-сообщений; их нет в исходном отчёте.
- Рабочий `topic` обменник RabbitMQ с долговременными очередями и отдельными воркерами. Он отличается от **учебного fanout варианта 3**; оба используют RabbitMQ.
- Возможность предварительно связать абонемент с `payment_id` и сроком `expires_at`, чтобы реакция на `payment.confirmed` могла его активировать без выдуманной длительности тарифа.
- Изолированные логические PostgreSQL-базы и локальная проекция завершённых тренировок в ReviewService.
- Имитация возврата платежа (никакого реального списания и возврата денег).

## По-прежнему неизвестно

1. Реальное распределение сервисов между тремя авторами.
2. Тарифы, длительности, стоимость и банковский API (отсутствуют в прежнем отчёте).
3. Подлинные скриншоты запуска RabbitMQ и Docker Compose на компьютере исполнителя.

## Проверки и ограничения

Локальные unit/component тесты на SQLite и моках HTTP/AMQP выполнялись. Нет проверки доставки через реальный брокер, нет Docker в доступной среде. Нет production-надежности: транзакционный outbox, механизм гарантированного восстановления после разрыва между commit и publish, автоматизированный повтор сообщений из DLQ и наблюдаемость не реализованы.
