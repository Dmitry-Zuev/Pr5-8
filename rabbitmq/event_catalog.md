# RabbitMQ — каталог доменных событий спортзала

Основа: бизнес-правила Event Storming из отчёта практик №1–4. **В исходных практиках определены события и взаимодействия, но не указаны поля транспортных сообщений и очереди.** Поэтому предложенные имена и JSON-поля ниже — технический проектный контракт практик №5–8.

## Учебный вариант 3 (задание 1 практики №5)

- Exchange `gym_exercise_3`: `fanout`, в учебном варианте нет сохранения сообщений.
- Очередь `<группа>_<фамилия>`, для примера `ikbo-66-23_zuev`: `durable=False`, `auto_delete=True`.
- Получатель ждёт сообщение, выбирает `random.randint(1, 5)` секунд, подтверждает `basic_ack`.
- Производитель только объявляет exchange, а consumer создаёт и привязывает очередь; сначала запускают consumer.

## Асинхронные бизнес-события (задание 2)

Основной обменник `gym.domain.events`: `topic`, `durable=True`. Сообщения `delivery_mode=2`, очереди устойчивые, подтверждение вручную после обработки. Неуспешная обработка приводит к переносу в `gym.failed.events`; ручная повторная отправка не автоматизирована.

Тело каждого сообщения:

```json
{
  "event_id": "UUID события",
  "type": "payment.confirmed",
  "occurred_at": "дата и время ISO 8601",
  "data": {"payment_id": "UUID платежа", "user_id": "UUID пользователя"}
}
```

| Из чьего события №1–4 | Ключ `routing_key` | Очередь / получатель | Реакция | `data` |
|---|---|---|---|---|
| «Платёж подтверждён» (Оплата) | `payment.confirmed` | `gym.subscriptions.payment-confirmed` / SubscriptionService | Активация **заранее связанного** абонемента, если известны `payment_id`, `user_id` и `expires_at` | `payment_id`, `user_id` |
| «Абонемент расторгнут» | `subscription.terminated` | `gym.payments.subscription-terminated` / PaymentService | Перевод подтверждённого тестового платежа в `refunded`; без банка | `subscription_id`, `payment_id`, `user_id` |
| «Тренировка завершена» | `training.finished` | `gym.reviews.training-finished` / ReviewService | Запись ID завершённой тренировки в локальную проекцию для разрешения отзыва | `training_id` |
| «Заявка подтверждена» | `tour.confirmed` | `gym.tours.tour-confirmed` / TourService | Запись в журнал для последующего планирования менеджером; дата не создаётся автоматически | `tour_id` |

**Отдельное ограничение:** событие `payment.confirmed` не активирует абонемент, созданный без ссылки на оплату и `expires_at`, так как эти сведения отсутствуют в работе №1–4 и не могут быть придуманы. Для демонстрации автоматической активации перед подтверждением платежа требуется создать абонемент с `payment_id` и указанным пользователем сроком.

Для синхронных проверок остаются HTTP/REST вызовы, предусмотренные практикой №6; Kafka в обновлённом проекте **не используется** по решению пользователя.
